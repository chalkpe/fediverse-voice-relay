# 운영과 복구

## 백업

PostgreSQL과 이용 서버 시크릿 파일은 함께 백업하세요. DB에는 릴레이의 설치 식별자가 들어 있습니다. 같은 설치의 프로세스는 같은 DB와 schema를 사용합니다.

## 녹음 상태 저장 방식의 전환

녹음 상태를 DB에 보관하는 버전과 LiveKit 속성에 쓰는 이전 버전을 같은 설치에서 동시에 서비스하지 않습니다. 이전 버전으로 가는 새 요청을 막고 진행 중인 요청을 정리한 뒤, 모든 제공자 프로세스를 새 버전으로 시작하세요. 새 버전은 시작할 때 `participant_tokens`에 녹음 SID와 값을 추가하는 migration을 적용합니다. 기존 배정, 토큰 세대와 설치 식별자는 유지합니다.

이전 버전 중에는 `recordingStatus` 능력 자체가 없으며 `recording` 필드를 거부하는 버전도 있습니다. 용량 조회와 상태 갱신이 서로 다른 버전에 도달하지 않도록 전환을 마친 뒤 이용 서버의 녹음 기능을 활성화하세요. HTTP 필드와 능력의 의미는 그대로입니다.

DB 백업은 migration 전에 보존합니다. 이전 앱으로 복구할 때도 모든 제공자 프로세스를 함께 전환하고, 이용 서버가 현재 SID의 녹음 상태를 다시 보고하도록 합니다. 이전 앱은 DB에 기록된 녹음 값을 읽지 않습니다. DB 복원은 별도 DB에서 먼저 확인하고, 복구할 앱 버전의 migration 이력과 함께 맞춥니다.

## 복구

백업이 있으면 서비스를 시작하기 전에 원래 PostgreSQL 백업과 이용 서버 시크릿 파일을 함께 복원하세요.

백업이 없거나 남은 방을 직접 정리해야 한다면 다음 순서로 처리합니다.

1. 해당 LiveKit을 사용하는 모든 제공자의 관리자와 함께 방 이름, 배정 기록, metadata, 참가자 상태를 대조합니다.
2. 소유 설치와 종료 여부를 확인합니다.
3. 소유권과 종료가 확인된 방만 LiveKit 관리 API에서 이름을 지정해 삭제합니다.
4. 삭제 결과를 확인합니다.

## 별도 설치로 DB 복제

별도 설치에 DB를 복제할 때는 원본 DB가 아닌 복제본 DB에서 작업하는지 확인하세요. 릴레이를 시작하기 전에 다음 SQL로 복제본의 설치 식별자를 새로 만듭니다.

```sql
UPDATE relay_installation SET installation_id = gen_random_uuid() WHERE singleton = true RETURNING installation_id;
```

행이 없으면 릴레이는 최초 실행에서 새 식별자를 만듭니다. 같은 설치의 백업을 복원할 때는 기존 식별자를 유지합니다. 백업 이후에 만들어진 방이 있을 수 있으므로 자동 정리를 켜기 전에 대조하세요.

## 배정 기록이 없는 방의 자동 정리

배정 기록이 없는 방의 자동 정리는 기본적으로 꺼져 있습니다. 소유권을 확인한 뒤에만 `reconcileOrphans: true`로 켭니다. 자동 정리는 DB 설치 식별자와 LiveKit 방 metadata가 일치하는 방을 정리합니다.

릴레이는 기존 DB에 배정 기록이 남은 이전 버전 방에 정상 종료와 lease 만료 정리를 적용할 수 있습니다.

## 설정 파일

`init`이 만든 `.env`와 `secrets/`는 안전하게 보관하세요. `databaseUrl`, `livekit.url`, `livekit.apiKey`, `livekit.apiSecret`, `livekit.verificationKeys`가 바뀌면 reload는 설정 전체를 거부합니다. 이 값들을 바꿀 때는 재시작과 별도 이전 절차가 필요합니다. DB 비밀번호는 기존 DB 볼륨에 저장된 비밀번호와 일치해야 하므로 `.env`만 바꾸어서는 교체할 수 없습니다. LiveKit 자체 설정도 LiveKit 쪽 변경 절차를 거쳐야 합니다.

공유 LiveKit이 릴레이의 활성 키가 아닌 다른 키로 갱신 토큰을 서명한다면 신뢰하는 서명 키를 `livekit.verificationKeys`에 추가합니다. 각 비밀은 32자 이상이어야 합니다. `apiKey`와 `apiSecret`은 계속 새 참여 토큰 발급과 LiveKit 관리에 사용하고, 추가한 키는 참여 토큰 검증에만 사용합니다. LiveKit에서 갱신 서명에 사용할 수 있는 키를 모두 등록하고, 키를 교체할 때는 두 설정을 함께 관리하세요. 단일 키 설치에는 이 설정이 필요하지 않습니다.

```json
"verificationKeys": [
  { "apiKey": "다른-LiveKit-키", "apiSecret": "여기에-32자-이상의-실제-비밀을-입력하세요-예시값" }
]
```

`init`의 주소와 시크릿 파일 경로는 Compose 내부 실행용입니다. Compose 밖에서 실행할 때는 실제 DB, LiveKit과 시크릿 파일 경로를 설정하고 API와 metrics를 신뢰된 인터페이스에만 바인딩하세요.

`screenShareLimits`는 모든 이용 서버에 전달할 선택적 화면 공유 화질 상한입니다. 항목을 생략하면 응답에도 상한이 없으며 릴레이는 제한 숫자를 지정하지 않습니다. 설정할 때는 [예제](examples/config.json)처럼 네 필드를 모두 양의 안전한 정수로 지정하세요. 예제의 1920×1080 픽셀, 초당 60프레임, 8,000,000 bit/s는 설정값의 예시이며 기본값이나 프로토콜 최대값이 아닙니다. 화면 공유 허용 여부는 이용 서버의 별도 권한 설정입니다.

이 설정을 reload하면 이후 용량 응답과 기존 방을 포함한 새 참여 응답에 새 상한이 적용됩니다. 진행 중인 방과 연결은 유지되며 이미 시작한 송출의 설정은 자동으로 바뀌지 않습니다. 이용 서버는 새 참여 응답을 참가자에게 전달해 이후 캡처와 게시에 적용해야 합니다.

다른 설정은 유효성 검사와 필요한 listener, TURN 준비가 성공하면 함께 적용됩니다. 한도를 줄이면 기존 예약은 유지되고 새 배정이 제한됩니다. 이미 성립된 HTTP 요청과 WebSocket은 listener를 바꾸어도 종료되지 않습니다. 공개 URL을 바꾸면 기존 배정은 생성 당시의 URL을 사용합니다. 해당 URL과 프록시 경로는 기존 배정의 연결이 끝날 때까지 유지하세요. 새 주소와 포트를 먼저 바인딩할 수 없으면 전체 변경이 거부됩니다.

Compose의 `config-init`은 릴레이와 LiveKit 설정을 각각 별도 볼륨으로 복사합니다. `secrets/config.json`을 편집한 뒤 다음 순서로 실행합니다. 첫 명령은 설정 사본을 교체하고, 둘째 명령은 실행 중인 릴레이의 적용 결과를 기다립니다. `secrets/livekit.yaml` 변경은 사본을 교체한 뒤 LiveKit을 재시작해야 적용됩니다.

```sh
docker compose run --rm --no-deps config-init
docker compose run --rm --no-deps admin reload
```

Compose 밖에서 실행할 때는 릴레이와 운영자 CLI에 같은 `VOICE_RELAY_CONTROL` Unix 소켓 경로를 지정하고 `node src/app/cli.ts reload`를 실행하세요. 기본 경로는 `/tmp/voice-relay/relay.sock`입니다. 부모 디렉터리는 릴레이 사용자가 소유해야 하며 다른 사용자가 접근할 수 없어야 합니다. 소켓에 접근하는 사용자는 reload를 요청할 수 있으므로 디렉터리를 신뢰하지 않는 사용자와 공유해서는 안 됩니다. 비정상 종료로 소켓이 남으면 릴레이가 실행 중인지 먼저 확인하고, 실행 중이 아닐 때만 소켓을 삭제하세요. 여러 릴레이 프로세스에는 각각 별도의 제어 소켓이 필요합니다.

시크릿 파일이 잠시 손상되거나 읽히지 않으면 실행 중인 서버는 마지막으로 검증한 시크릿을 유지합니다. 파일을 복구한 뒤 시크릿 교체 결과를 확인하세요. 설정 reload에서 새 시크릿 파일을 검증할 수 없으면 전체 변경이 거부됩니다.

설정과 시크릿 파일을 직접 복사하거나 복원할 때는 소유자만 읽고 쓸 수 있게 보호하세요. 원격 PostgreSQL과 LiveKit에 연결할 때는 인증서를 검증하는 TLS를 사용합니다. Compose 내부 연결은 사설 네트워크 밖으로 노출하지 않습니다.

역방향 프록시의 접근 로그에는 RTC 요청의 쿼리 문자열을 기록하지 않습니다. 쿼리의 `access_token`은 참가자 토큰입니다. 제공된 Caddy 예제는 접근 로그를 켜지 않습니다.

## 용량

릴레이 전체에서 예약할 수 있는 최대 슬롯 수와 방 수는 `secrets/config.json`의 `maxSlots`, `maxRooms`로 정합니다. 이용 서버별 한도는 `client add`의 `--max-slots`, `--max-rooms`로 정합니다. 새 통화는 두 한도에 모두 여유가 있어야 시작됩니다.

슬롯은 통화방 정원만큼 미리 잡아 두는 참가자 자리입니다. 릴레이는 한 방을 열 때 그 방의 최대 참가자 수만큼 슬롯을 예약하므로, 슬롯은 여러 방이 나눠 씁니다. 그래서 방 수가 남아 있어도 슬롯이 먼저 찰 수 있습니다. 이용 서버마다 필요한 방의 정원을 더해 `--max-slots`를 정하세요.

## 모니터링

별도 metrics listener는 기본적으로 `127.0.0.1:9090`에 바인딩됩니다. Compose 예제에서는 컨테이너 내부 주소로 바인딩하며, 호스트 포트는 게시하지 않습니다.

같은 Compose 네트워크에 연결된 Prometheus에는 다음 대상을 설정하세요.

```yaml
scrape_configs:
  - job_name: voice-relay
    static_configs:
      - targets: ['relay:9090']
```

같은 Docker 네트워크의 컨테이너는 이 주소로 접근할 수 있습니다. 호스트에서 접근할 때는 Docker 네트워크 설정에 따라 포트 게시나 프록시가 필요합니다. 외부에서 수집할 때는 다음 중 하나를 선택하세요.

- 사설망이나 VPN을 사용합니다.
- 배포 계층에서 TLS와 표준 HTTP 인증을 구성합니다.

공개 API 프록시는 metrics listener로 연결하지 않습니다.

`/health`는 PostgreSQL 연결을 확인합니다. LiveKit과 TURN의 준비 상태는 확인하지 않습니다.

## LiveKit 접근 경계

참가자 토큰의 취소 검사는 릴레이의 토큰 검사와 RTC HTTP·WebSocket 진입 경로에 적용됩니다. 자가 호스팅 LiveKit은 참가자 퇴장이나 권한 변경만으로 기존 토큰을 무효화하지 않습니다. 따라서 LiveKit 시그널링과 관리 API 포트는 릴레이와 신뢰된 관리 네트워크에만 노출합니다. 이용자가 LiveKit에 직접 연결할 수 있으면 릴레이의 취소 검사를 우회할 수 있습니다.

Compose 예제는 LiveKit 시그널링 포트 7880을 호스트에 게시하지 않고, 미디어용 7881/TCP와 7882/UDP만 게시합니다. Caddy 예제는 릴레이 포트만 프록시합니다. 다른 프록시와 방화벽, Docker 네트워크도 같은 접근 경계를 유지하도록 구성하세요. 신뢰할 수 없는 컨테이너는 내부 네트워크에 연결하지 않습니다.

## TURN

필요하면 LiveKit 내장 TURN이나 별도 TURN 서버를 구성합니다. 릴레이 설정의 `iceServers`에 접속 URL과 발급받은 자격 증명을 넣습니다.

## 이용 서버 시크릿 변경과 장애 복구

이용 서버를 비활성화해도 유효한 시크릿으로 기존 배정과 참가자 정보를 조회할 수 있습니다. 시크릿이 유출되면 네트워크 접근을 제한하고 시크릿을 교체하세요. 교체하면 기존 시크릿은 즉시 무효화됩니다.

릴레이는 이용 서버 등록과 시크릿 교체를 시크릿 파일 옆의 잠금 디렉터리로 직렬화합니다. 같은 시크릿 파일을 관리하는 모든 명령은 같은 공유 디렉터리와 같은 경로를 사용해야 합니다. 파일 시스템은 디렉터리 생성과 같은 디렉터리 안의 rename을 원자적으로 지원해야 합니다.

시크릿 파일을 직접 편집하거나 다른 경로 별칭으로 쓰는 작업은 이 잠금에 참여하지 않습니다. 따라서 이런 작업은 시크릿 관리 명령과 동시에 실행하지 않습니다.

이용 서버 등록은 DB 트랜잭션과 시크릿 파일을 함께 다루지만, 두 저장소를 하나의 원자적 트랜잭션으로 묶지는 못합니다. 중단되거나 DB 연결이 끊긴 뒤에는 시크릿 파일 옆에 `.pending` 파일이 남을 수 있습니다. `.pending` 파일에는 시크릿이 들어 있습니다. 따라서 `.pending` 파일은 시크릿 파일과 같은 권한으로 보호합니다. `.pending` 파일은 삭제하지 않습니다.

DB와 파일이 다시 쓰기 가능한 상태에서 `client add` 또는 `client rotate-secret`을 실행하세요. 이때 명령은 저장된 이용 서버가 있는지 확인합니다. 명령은 시크릿을 복구하거나 미완료 시크릿을 제거한 뒤 계속 진행합니다.

실패한 생성 명령이 자격 증명을 출력하지 못했다면 복구한 뒤 해당 이용 서버의 시크릿을 교체하세요. 그러면 릴레이가 새 자격 증명을 발급합니다.

프로세스가 강제 종료되면 시크릿 파일 옆에 `.lock` 디렉터리가 남을 수 있습니다. 모든 이용 서버 관리 명령이 끝났는지 확인하세요. 모든 명령이 끝난 뒤에만 빈 잠금 디렉터리를 직접 제거합니다. 그다음 앞의 시크릿 복구 절차를 실행하세요.

실행 중인 명령의 잠금을 제거하면 보호가 깨집니다. `.pending` 파일을 삭제해도 보호가 깨집니다.

파일 시스템 장애나 전원 손실은 DB와 파일의 동시 내구성을 깨뜨릴 수 있습니다. 따라서 DB와 시크릿 파일을 함께 백업하고, 복구한 뒤에는 결과를 확인하세요.

## 배정 생성 결과가 불명확한 경우

SFU 방 생성 요청의 결과가 불명확하거나 생성 중 프로세스가 종료되면 릴레이는 해당 배정의 `creation_inflight` 표시와 예약을 보존합니다.

릴레이는 안전한 종료를 확정할 수 없으므로 같은 배정 시도(generation)의 취소 요청에 `503`을 반환합니다.

방이 현재 보이지 않는다는 이유만으로 `creation_inflight` 표시를 지우지 않습니다. 같은 이유로 다른 제공자에 재배정하지도 않습니다.

관리자는 SFU 운영 측에서 이전 생성 요청이 더 이상 실행될 수 없는지 확인합니다. 관리자는 해당 설치와 방의 상태도 함께 조사합니다. 확인할 수 없으면 릴레이는 예약을 유지합니다.
