# 음성 릴레이 프로토콜 v1

이 문서는 연합우주 소프트웨어 개발자가 음성 릴레이 제공자를 구현하거나 이용하는 방법을 설명합니다. 프로토콜은 이용 서버와 제공자 사이의 음성 통화와 화면 공유를 다룹니다. 이용 서버 간 사용자·방 식별, 초대와 ActivityPub 통화 연합은 각 소프트웨어의 연합 계층에서 담당합니다.

제공자는 이용 서버를 인증하고 통화방 용량을 예약하며 LiveKit 시그널링을 중계합니다. 이용 서버는 사용자를 인증하고 방의 접근 권한을 판정하며 통화 UI를 제공합니다.

HTTP 메서드와 경로, 요청·응답 필드와 오류 코드는 실행 중인 제공자의 `/openapi.json`을 따릅니다. 같은 명세는 `/docs`에서도 볼 수 있습니다. 이 문서는 인증, 상태 전이와 복구 규칙을 설명합니다. 예제의 `/voice-relay/v1`은 제공자 API의 기본 경로이며, 운영 통신에는 HTTPS를 사용합니다.

## 이용 순서와 식별자 경계

1. 제공자는 이용 서버를 등록하고 서버 간 인증 시크릿을 발급합니다.
2. 이용 서버는 용량을 확인한 뒤 방을 식별할 `roomKey`와 이번 시도의 `generation`을 정하고 배정을 요청합니다.
3. 이용 서버는 각 사용자의 방 참여 권한을 확인하고 참가자별 참여 토큰을 요청합니다.
4. 이용 서버는 시그널링을 중계하고, lease를 갱신하며 이벤트 피드를 관리합니다.
5. 통화가 끝나면 이용 서버는 제공자에게 종료를 요청하고 종료 확인을 받습니다. 요청 결과가 불명확하면 같은 제공자에서 상태를 복구합니다.

`roomKey`와 사용자 ID는 해당 이용 서버의 범위에서 해석합니다. 같은 통화의 참가자들은 서로 구분되는 identity를 사용합니다. 재접속한 세션은 제공자가 반환한 session ID로 구분합니다. 제공자는 전달받은 식별자가 이용 서버와 배정에 일치하는지 검사합니다. 사용자 로그인과 방 참여 권한은 이용 서버가 판정합니다.

## 이용 서버 등록과 인증

제공자는 이용 서버의 HTTPS origin을 등록하고 내부 이용 서버 ID를 만듭니다. 이때 예약할 수 있는 슬롯 수와 동시 방 수, 화면 공유 허용 여부를 정합니다. 같은 origin은 한 번만 등록할 수 있습니다. 이용 서버마다 시크릿 하나를 발급하며 두 서버의 서버 측에만 보관합니다. 이용 서버는 브라우저의 로그인 정보나 쿠키를 제공자에게 전달하지 않습니다.

이용 서버는 일반 API 요청과 서버 측 WebSocket 업그레이드 요청에 `Authorization: Bearer <JWT>`를 보냅니다. 서버 간 시크릿과 JWT는 브라우저에 전달하지 않습니다. HTTPS 연결에서는 제공자 인증서를 검증합니다.

공개 URL이 바뀌어도 기존 배정의 미디어 제공자 주소는 생성 당시의 공개 origin을 유지합니다. 모든 새 제어 요청은 현재 릴레이 공개 origin을 audience로 사용합니다.

JWT는 표준 JOSE 라이브러리로 생성합니다. 보호된 헤더의 `alg`는 `HS256`, `typ`은 `voice-relay-client+jwt`입니다. `kid`와 `sub`는 사용하지 않습니다. 다른 알고리즘이나 외부 키 URL은 사용할 수 없습니다. 발급받은 시크릿 문자열의 UTF-8 바이트로 서명합니다.

| claim | 값 |
| --- | --- |
| `iss` | 등록된 이용 서버의 정규화된 공개 HTTPS origin |
| `aud` | 제공자의 공개 HTTPS origin |
| `iat` | 발급 시각을 나타내는 Unix 초 |
| `exp` | 만료 시각을 나타내는 Unix 초 |

`exp`는 `iat`보다 나중이고 최대 60초 뒤여야 합니다. 제공자는 발급 시각과 만료 시각을 확인할 때 최대 5초의 시각 오차를 허용합니다. JWT는 유효기간 안에 재사용할 수 있습니다. HTTPS는 요청 경로와 본문을 전송하는 동안 보호합니다. 제공자는 JWT에 경로·본문 해시나 일회용 nonce를 요구하지 않습니다. 배정 요청의 중복 처리는 아래 generation 규칙을 따릅니다.

제공자는 인증된 이용 서버별 요청을 최근 60초 동안 최대 300회로 제한합니다. 일반 API 요청과 RTC WebSocket 업그레이드는 같은 한도를 사용합니다. 한도에 도달하면 `429 RATE_LIMITED`를 반환합니다. 이 한도는 같은 DB를 쓰는 제공자 프로세스 사이에서 공유됩니다. DB에 접근할 수 없으면 요청을 허용하지 않습니다.

요청 본문은 최대 64 KiB입니다. 본문은 UTF-8로 해석할 수 있어야 합니다. 제공자는 잘못된 JSON 요청을 거부합니다. 정해진 필드가 있는 요청 객체에서는 명세에 없는 본문 필드도 거부합니다.

`/health`, `/docs`, `/openapi.json`에는 이용 서버 JWT가 필요하지 않습니다. `/livekit/webhook`에서 제공자는 원본 본문으로 LiveKit의 `Authorization` 서명을 검증합니다. 일반 API의 오류 코드와 상태는 OpenAPI 응답을 기준으로 처리합니다.

제공자는 `iss`로 로컬 등록을 조회하고 해당 시크릿으로 서명과 클레임을 검증합니다. 시크릿 교체는 이전 시크릿을 즉시 무효화합니다. 이용 서버는 새 시크릿을 사용해 새 제어 요청에 서명합니다. 시크릿 교체 자체는 통화방이나 미디어 연결을 종료하지 않습니다.

이용 서버를 비활성화한 뒤에도 유효한 시크릿으로 기존 배정을 조회하고 종료를 확인할 수 있습니다. 새 배정, 참여와 lease 갱신은 허용되지 않습니다.

## 배정, 정원과 복구

이용 서버는 통화방을 처음 배정할 때 `roomKey`, `generation`, `slots`를 정합니다. `roomKey`는 방을 식별하고, `generation`은 이번 배정 시도를 식별하며, `slots`는 방의 최대 참가자 수입니다. 새 배정 시도에는 새 `generation`을 만들고, 같은 시도를 재시도할 때는 같은 `generation`을 유지합니다.

제공자는 방 정원 전체를 원자적으로 예약합니다. 예약은 이용 서버별 한도와 제공자 전체 한도를 모두 따릅니다. 슬롯은 현재 접속 인원 수가 아니라 예약한 최대 참가자 수입니다. `pending`, `active`, `ending` 배정은 슬롯과 방 한도를 계속 차지합니다. 용량 조회는 조회 시점의 참고값이며, 실제 배정 성공은 배정 요청의 결과로 확인합니다.

용량 응답의 현재 참가자 수는 최대 2초 전의 값일 수 있습니다.

같은 이용 서버, `roomKey`, `generation`, `slots`의 배정 요청은 멱등적입니다. 같은 이용 서버, `roomKey`, `generation`에 다른 슬롯 수를 요청하거나 같은 방에 종료되지 않은 다른 `generation`이 있으면 충돌합니다. 이미 `ended`가 된 같은 `generation`을 재시도해도 새 방은 만들어지지 않습니다.

제공자는 다음 배정 상태를 사용합니다.

- `pending`: 슬롯을 예약했지만 LiveKit 방 준비는 끝나지 않은 상태입니다.
- `active`: 방이 준비되어 유효한 lease 안에서 참여와 갱신이 가능한 상태입니다.
- `ending`: 종료를 요청했지만 LiveKit 방 삭제 확인은 끝나지 않은 상태입니다.
- `ended`: 제공자가 방 삭제를 확인한 상태입니다. 종료 요청을 다시 보내면 종료된 결과를 반환합니다.

배정 결과가 불명확하면 이용 서버는 같은 제공자에서 복구합니다. 같은 `generation`과 슬롯 수로 재시도하거나 `roomKey`와 `generation`으로 조회합니다. `pending`도 예약으로 취급합니다. 네트워크 오류나 시간 초과만으로 배정 실패 또는 방 종료를 확정하지 않습니다.

다른 제공자에 재배정하기 전에 기존 제공자의 `ended` 상태 또는 아래 취소 완료를 확인해야 합니다. 새 `generation`으로 다시 시작할 때도 같은 확인이 필요합니다. lease 만료만으로 종료를 확정하지 않습니다.

용량 응답의 `capabilities.cancelPending`이 `true`이면 이용 서버는 해당 시도를 취소할 수 있습니다. 이용 서버는 OpenAPI의 취소 작업에 `roomKey`와 `generation`을 보냅니다. 제공자는 이 조합의 취소 기록을 영구 보존합니다. 이미 방을 만들고 있었다면 제공자는 LiveKit 종료를 확인한 뒤에만 `{ "state": "ended" }`를 반환합니다. 취소 이후에 도착한 같은 `generation`의 배정 요청은 `409 ALLOCATION_CONFLICT`로 거부합니다. 취소는 멱등적입니다.

이용 서버가 비활성화된 뒤에도 유효한 시크릿으로 취소할 수 있습니다.

제공자는 이용 서버별로 최대 100,000개의 서로 다른 generation과 방 키·generation의 UTF-8 바이트 합계 16 MiB를 누적 기록합니다. 종료와 취소 후에도 이 사용량은 줄지 않습니다. 한도에 도달하면 새로운 조합을 거부합니다. 기존 조합의 재시도와 취소는 계속 처리합니다.

종료 확인에 실패하면 제공자는 예약을 유지하고 `503 PROVIDER_UNAVAILABLE`을 반환합니다. 이용 서버는 같은 취소를 재시도합니다. SFU 방 생성 결과 자체가 불명확하면 제공자는 완료를 안전하게 확정할 수 없으며, 이때 취소가 계속 `503`으로 남을 수 있습니다.

취소 능력이 없거나 `false`인 제공자에서는 기존 제공자에 대한 복구를 계속합니다. 조회 결과가 404여도 늦게 도착한 배정 요청이 실행될 수 있습니다. 이용 서버는 404만으로 다른 제공자에 다시 배정하지 않습니다. 새 시도에는 새 `generation`을 사용합니다.

lease는 120초이며, 이용 서버는 30초마다 갱신합니다. 제공자는 lease가 만료된 배정의 종료를 재시도합니다. 비활성화된 이용 서버의 배정과 `ending` 배정의 종료도 재시도합니다. 참가자가 없는 방은 빈 상태가 60초를 넘으면 종료 대상이 됩니다.

LiveKit 종료 확인에 실패하면 제공자는 `ending`을 유지하며 예약을 해제하지 않습니다.

## 참가자와 권한

이용 서버는 참가자 식별자를 참여 요청의 identity로 정합니다. user ID는 해당 이용 서버의 범위에서 사용합니다. 제공자는 이용 서버가 활성 상태인지, 배정이 유효한지 확인한 뒤 LiveKit 토큰을 발급합니다.

제공자는 배정마다 예약 슬롯 수의 32배까지 서로 다른 identity를 기록합니다. 한도에 도달하면 새로운 identity의 참여 요청은 `429 CAPACITY_EXCEEDED`로 거부합니다. 이미 기록된 identity의 재참여와 토큰 취소는 계속 허용합니다. 기록은 배정이 종료될 때 삭제됩니다.

이용 서버와 참여 요청이 모두 화면 공유를 허용할 때만 화면 공유와 화면 공유 오디오를 게시할 수 있습니다. 마이크 게시와 구독은 허용합니다. 일반 데이터 게시와 참가자의 임의 메타데이터 변경은 허용하지 않습니다.

화면 공유 허용 여부는 참여 요청과 권한 변경 요청의 `allowScreenShare` 필드로 전달합니다. 용량 응답과 참가자 정보도 같은 필드 이름을 사용합니다.

용량(`GET /voice-relay/v1/capacity`)과 참여(`POST /voice-relay/v1/allocations/{id}/join`) 응답의 `screenShareLimits` 객체는 선택 항목입니다. 제공자가 상한을 설정하지 않으면 이 객체를 생략하며 릴레이는 제한 숫자를 지정하지 않습니다. 설정하면 `maxWidth`와 `maxHeight`는 캡처 너비와 높이의 픽셀 상한, `maxFrameRate`는 초당 프레임 상한, `maxBitrate`는 화면 공유 비디오 인코딩의 bit/s 상한입니다. 네 값은 모두 양의 안전한 정수입니다. 설정된 객체는 화면 공유가 허용되지 않은 경우에도 전달되며 권한을 부여하지 않습니다.

이용 서버는 참여 응답의 값을 참가자에게 전달하고 화면 캡처와 비디오 게시에 모두 적용해야 합니다. LiveKit JS SDK에서는 캡처의 `resolution.width`, `resolution.height`, `resolution.frameRate`와 게시의 `screenShareEncoding.maxBitrate`, `screenShareEncoding.maxFramerate`를 사용합니다. 여러 인코딩을 동시에 보내면 비디오 인코딩 비트레이트 합계가 `maxBitrate`를 넘지 않게 해야 합니다. 예를 들어 단일 VP8 인코딩으로 게시할 때 `simulcast: false`와 `backupCodec: false`를 지정할 수 있습니다. 화면 공유 오디오는 이 비트레이트에 포함하지 않습니다.

이 제한은 협조하는 송출자가 적용하는 운영 정책입니다. LiveKit 권한은 화면 공유 게시 자체를 허용하거나 금지하지만, 이 응답만으로 수정된 송출자의 해상도, 프레임 수 또는 비트레이트를 서버가 강제하지는 않습니다. 참고: [LiveKit JS SDK 옵션](https://github.com/livekit/client-sdk-js/blob/main/src/room/track/options.ts), [LiveKit 서버 측 구독 화질 제한 논의](https://github.com/livekit/livekit/issues/4295).

설정 reload가 완료된 뒤 시작한 용량과 새 참여 요청에는 새 상한이 적용됩니다. reload와 겹치는 요청은 이전 값이나 새 값을 반환할 수 있습니다. 기존 배정에 고정하지 않으므로 reload 전후 응답이 다를 수 있습니다. 이미 연결된 참가자에게 새 값이 자동으로 전달되거나 적용되지는 않습니다. 이용 서버는 각 참여 응답의 값을 사용해야 합니다.

용량 응답의 `capabilities.includeIceServers`가 `true`이면 참여 요청에 `includeIceServers`를 지정할 수 있습니다. `false`로 지정하면 제공자는 TURN 발급을 건너뛰고 `iceServers: null`을 반환합니다. 필드를 생략하거나 `true`로 지정하면 제공자의 ICE 서버 목록을 요청합니다. `null`은 제공자 목록이 없다는 뜻이고, 빈 배열은 명시적으로 빈 목록을 제공한다는 뜻입니다.

제공자가 Cloudflare TURN을 설정하면 정적 `iceServers` 대신 동적으로 발급한 목록을 사용합니다. 동적 발급에 실패하면 참여 요청이 실패하며 정적 목록으로 대체하지 않습니다. Cloudflare TURN이 설정되지 않았으면 정적 목록을 사용합니다.

참가자를 퇴장시키거나 화면 공유 권한을 해제하면 제공자는 해당 배정과 identity에 발급된 이전 참여 토큰을 무효화합니다. LiveKit이 기존 연결에서 자동 발급한 갱신 토큰에도 같은 무효화가 적용됩니다. 이용 서버가 방 참여 권한을 다시 확인한 뒤 새 참여를 요청하면 새 토큰을 받을 수 있습니다. 화면 공유 권한을 해제할 때는 새 참여 요청에도 변경된 권한을 반영해야 합니다.

이용 서버는 같은 참가자의 참여 요청과 퇴장 또는 권한 축소를 순서대로 처리해야 합니다. 이전 권한으로 승인한 참여 요청은 퇴장이나 권한 축소 뒤에 실행되지 않아야 합니다.

마이크 음소거는 요청 시 발행된 마이크 트랙에 적용됩니다. 참가자가 새 트랙을 발행하는 것을 금지하지 않습니다.

이용 서버는 참가자 상태를 갱신할 때 현재 참가자의 session ID를 보냅니다. session ID가 현재 LiveKit 참가자와 다르면 제공자는 상태를 적용하지 않고 `accepted: false`를 반환합니다. 참가자가 해당 배정의 참여 토큰으로 연결되지 않았을 때도 같습니다. 이용 서버는 오래된 세션의 상태로 새 세션을 덮어쓰지 않아야 합니다. 참가자 퇴장, 마이크 음소거와 화면 공유 권한 변경에는 명세에 정의된 해당 작업을 사용합니다.

용량 응답의 `capabilities.recordingStatus`가 `true`이면 상태 갱신에 `recording`을 보낼 수 있습니다. 이 값이 없거나 `false`이면 이용 서버는 `recording`을 보내지 않습니다. 이용 서버는 녹음을 승인하기 전에 이 값을 확인하고, 지원하지 않는 제공자에서는 녹음을 승인하지 않습니다. 이때도 일반 통화와 `recording` 없는 상태 갱신은 계속 사용할 수 있습니다.

상태 갱신의 `recording`은 선택 항목입니다. 이용 서버가 `true`나 `false`를 보내면 제공자는 요청한 session ID의 녹음 상태를 바꿉니다. 필드를 생략하면 제공자는 그 세션의 녹음 상태를 그대로 둡니다. 녹음을 식별하는 이용 서버 내부의 ID는 제공자에 보내지 않으며, 명세에 없는 필드는 다른 요청과 같이 거부됩니다.

제공자는 녹음 상태를 session ID별로 보관하고, snapshot 참가자의 `recording`에 현재 session ID의 상태를 반환합니다. 같은 identity가 새 세션으로 다시 연결되면 `recording`은 `false`에서 시작합니다. 이용 서버는 새 session ID로 녹음 상태를 다시 보내야 합니다.

제공자는 수락한 녹음 상태와 `participant` 이벤트, snapshot revision을 같은 DB 트랜잭션에 기록합니다. 녹음 상태를 LiveKit 속성에 쓰지 않으므로, DB 잠금을 잃은 요청의 지연된 SFU 쓰기는 나중에 성공한 녹음 보고를 뒤집지 않습니다.

같은 SID의 일반 상태 요청은 제공자가 배정 잠금을 얻은 순서로 처리합니다. 이용 서버는 이전 상태를 뒤늦게 재시도하지 않도록 상태 보고를 순서대로 보냅니다. 이용 서버가 정한 순번을 제공자가 판정하는 계약은 없습니다.

LiveKit은 session ID를 조건으로 참가자 상태를 쓰는 API를 제공하지 않습니다. 제공자는 마이크와 소리 끄기 상태를 쓰기 전후의 session ID를 확인하고, 다른 세션에 닿은 쓰기는 되돌린 뒤 `accepted: false`를 반환합니다. 녹음 상태는 이때 DB에 기록하지 않습니다. 마이크와 소리 끄기 상태는 이때 지워질 수 있으며, 새 세션의 다음 상태 갱신으로 다시 맞춰집니다.

`capabilities.recordingStatus`가 없는 이전 버전의 제공자는 `recording`이 있는 상태 갱신을 `400 INVALID_REQUEST`로 거부하고 snapshot에 `recording`을 반환하지 않습니다.

## 이벤트, snapshot과 순서

이용 서버는 활성 이벤트 피드를 약 2초마다 조회합니다. 제공자가 반환한 cursor를 다음 요청에 그대로 사용합니다. cursor는 이용 서버에 종속되므로 다른 이용 서버에 재사용할 수 없습니다. 한 응답에는 최대 100개의 이벤트가 ID 오름차순으로 담깁니다.

첫 요청에서 cursor를 생략하면 보존 중인 이벤트를 처음부터 조회합니다. 이후에는 반환된 cursor로 이어 갑니다. 첫 조회에서 이전에 삭제된 이벤트가 있어도 `gap`은 참이 되지 않습니다. 이미 존재하는 배정을 복구할 때는 보유한 배정들의 snapshot도 조회합니다. 응답의 상태 반영을 끝낸 뒤 cursor를 저장합니다. 상태 반영에 실패하면 같은 cursor부터 다시 처리합니다.

이벤트 ID와 snapshot revision은 십진수 문자열입니다. 이용 서버는 두 값을 충분히 큰 정수로 비교하며, 문자열 사전순으로 비교하지 않습니다. 이용 서버는 이벤트를 배정 ID와 `generation`에 연결합니다. 오래된 `generation`의 이벤트가 현재 통화를 바꾸지 않도록 합니다.

참가자 변화 등 이벤트를 받으면 이용 서버는 해당 배정의 snapshot을 조회해 실제 상태를 맞춥니다. 이전 revision의 snapshot으로 더 새로운 상태를 덮어쓰지 않습니다.

제공자는 참가자 목록을 가져오기 전에 snapshot revision을 읽습니다. 이용 서버는 목록과 revision을 하나의 원자적 시점으로 가정하지 않습니다. 이용 서버는 해당 revision보다 뒤의 이벤트를 계속 처리하고, 필요할 때 snapshot을 다시 조회합니다.

cursor에 대해 `gap: true`가 오면 보존 기한 때문에 일부 이벤트가 빠졌을 수 있습니다. 이용 서버는 관련 배정 전체를 snapshot으로 다시 맞춘 뒤 피드를 계속 처리합니다. 이벤트는 24시간 보존 대상으로 관리합니다.

## RTC와 토큰

제공자는 배정에 종속된 RTC HTTP 요청과 WebSocket 업그레이드를 고정된 LiveKit `/rtc` 경로로 전달합니다. 이용 서버는 브라우저의 시그널링 연결을 서버 측에서 중계합니다. 제공자에 보내는 업그레이드 요청에는 이용 서버 JWT를 Bearer 인증으로 보냅니다. 서버 간 시크릿은 브라우저에 전달하지 않습니다. 미디어는 시그널링 중계와 별도로 제공자의 LiveKit 또는 TURN에 연결됩니다.

RTC URL에는 `access_token`이 정확히 하나 있어야 합니다. 제공자는 토큰의 서명과 만료를 확인합니다. 제공자는 이용 서버, 배정, `generation`과 LiveKit 방 권한을 확인합니다. 요청된 배정과 일치할 때만 연결을 허용합니다.

우회 경로나 다른 upstream 주소를 지정할 수 없습니다. WebSocket 프레임 크기는 1 MiB로 제한됩니다.

제공자가 발급하는 LiveKit 방 이름은 `voice-relay:<clientId>:<allocationId>`입니다. 토큰의 metadata는 JSON 객체이며 `clientId`, `allocationId`, `generation`, `userId`와 취소 검증용 `tokenGeneration`을 포함합니다. 토큰 검사 시 서명과 만료를 확인합니다. metadata의 이용 서버, 배정, `generation`과 해당 방의 `roomJoin` 권한도 확인합니다. 참가자 목록도 같은 이용 서버, 배정, `generation`에 속하는 metadata를 기준으로 구분합니다.

이전 형식처럼 `tokenGeneration`이 없는 참여 토큰은 허용하지 않습니다. 릴레이를 새 버전으로 전환한 뒤에는 이용 서버가 방 참여 권한을 확인하고 새 참여 토큰을 발급받아야 합니다. 최초 참여 토큰의 유효기간은 2분입니다. LiveKit은 연결 중 갱신 토큰을 발급할 수 있습니다. 재접속이나 후속 검증에는 실제로 발급된 토큰을 사용합니다. 제공자의 토큰 검사 API로 소속 배정과 `generation`을 확인합니다. 검증하지 않은 토큰의 내용에서 upstream URL을 가져와 접속하지 않습니다.

OpenAPI는 HTTP 업그레이드까지 기술합니다. 이후 WebSocket 프레임과 미디어 전송 자체는 기술하지 않습니다.
